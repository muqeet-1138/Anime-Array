Technology

How it is built, and why it is built that way

Anime Array is a self-hosted, server-rendered application. This page describes the approach and the reasoning behind it. It deliberately does not document internals.

What this page covers, and what it does not

Anime Array is a self-hosted, server-rendered web application that serves complete HTML over HTTPS, calls its AI and advertising integrations from the server, and caches its output at the edge. That sentence is the honest summary. Everything below is the reasoning behind it.

This page explains how the platform is put together. It does not publish the stack inventory, the server configuration, the deployment layout, the file structure, dependency versions, credential configuration or any operational detail. That is not secrecy for its own sake — a small independent site gains nothing from publishing an inventory of its own moving parts to people looking for weaknesses, and the interesting engineering questions can be answered without it.

A note for reviewers

If you are looking for a vulnerability report rather than an architecture explanation, the private route is in SECURITY.md. If you are looking for how to contribute, the process is in CONTRIBUTING.md.

The governing idea

A small project cannot afford fragile dependencies. Every architectural choice on Anime Array comes back to one question: can one person understand this, trace it, and repair it on a bad evening without a runbook?

That question resolves most arguments on its own. Where there was a choice between something clever and something comprehensible, the comprehensible option has won almost every time — not because cleverness is bad, but because the cost of cleverness is paid at the worst possible moment, which is when it has already broken and nobody remembers why it was written that way.

The second filter is narrower: does this help someone on a slow phone on mobile data? A feature that works beautifully on fast broadband and is unusable on a throttled mobile connection does not ship, regardless of how good it looks in a screenshot.

Server-rendered HTML

Every page on Anime Array arrives complete from the server. There is no single-page application shell, no client-side router, and no dependency on a framework running in the browser to produce the content a visitor is reading.

This has a concrete, measurable benefit rather than an aesthetic one. Content is present in the first response, which means it is present for a reader on a slow connection, for a crawler, for a screen reader that attaches after load, and for anyone whose JavaScript failed to execute for any reason at all. There is no second request to discover the page you already asked for.

It also makes the failure mode much better. When client-side rendering fails, the failure is usually a blank page with an error somewhere in a console most visitors will never open. When server-side rendering fails, the failure is a single failed request — obvious, logged, attributable, and fixable by one person who can see the actual cause.

Progressive enhancement

Core reading, character conversation and the AI assistant work without JavaScript. What JavaScript adds is polish — responses streaming in word by word rather than appearing all at once, share cards, image generation, instant history — never basic access.

The test applied to every feature before it ships is deliberately blunt: if the page is useful with scripting disabled, the feature is allowed. If it is only useful with scripting enabled, it needs a reason strong enough to be written down, and there are very few of those.

This is also why the platform feels fast rather than merely loading quickly. Responses begin arriving immediately and render progressively, so time-to-first-meaningful-word is short even when time-to-complete is long. On a throttled connection that difference is the whole experience.

Server-side integrations

Third-party AI and advertising calls are made from the server rather than from the visitor's browser. This is a security decision first and a performance decision second.

Keeping those calls server-side means API credentials, service account details and integration identifiers never appear in page source, never reach the browser, and cannot be extracted by anyone viewing it. It also means the requests are not competing with the visitor's own connection for bandwidth, and it means a failed integration degrades into a slower response rather than an error on screen.

The consequence is that pages carry less third-party code than most sites of comparable function, which directly improves how quickly a page becomes usable on mobile data.

Render-time configuration

Behaviour on Anime Array is applied while a page is being produced rather than stored inside the content that page contains.

This has one dominant practical benefit: every change is reversible in a single step. Turning something off, correcting a mistake or rolling back a change means removing or restoring one unit of code, rather than repairing database rows that were written into posts, templates or option tables. It is the reason the platform has never been down for a long period, and it is the reason mistakes are cheap enough that shipping small changes often is safer than shipping one large change rarely.

The second benefit is immediacy. A configuration change takes effect on the next request rather than after a cache expiry window or a manual purge.

Caching and delivery

Static assets and page output are cached close to the visitor. Pages are compressed in transit, served over HTTPS, and cached with sensible headers so a repeat visit costs very little.

Cache invalidation is handled deliberately rather than reactively, because a stale page published to the world is worse than a slow page. When something important changes, the cache is purged rather than left to expire.

Assets and images

Images are served at the size they are displayed at, in modern formats, with dimensions declared so the layout does not jump while they load. Fonts and stylesheets are sized to avoid blocking the first render unnecessarily. Space is reserved for content that arrives dynamically, so streaming responses do not push the rest of the page around as they appear.

None of this is exotic. It is simply the list of things that are checked before a feature is called finished, and each one has caused a visible problem at some point on this or any other site.

Accessibility in the output

Accessibility is a property of the markup, not a layer applied afterwards, which is why the platform can treat it as a requirement rather than a retrofit.

  • Native elements first. Buttons are buttons and links are links, chosen by behaviour rather than appearance, so keyboard behaviour and semantics come for free.
  • Real heading hierarchy. Heading levels describe document structure. They are not chosen to produce a particular font size.
  • Visible focus. A focus indicator that does not rely on colour alone, visible against the actual background it appears on.
  • Live regions for streaming. Character and assistant responses are announced as they arrive, so a screen reader user is not left guessing whether anything is happening.
  • Described errors. Validation failures are stated in words, not indicated by a colour change.
  • Reduced motion honoured. Animation, transitions and smooth scrolling respect the operating system preference.

Full detail on the accessibility position is on the about page.

Search and answer engines

Anime Array is built to be readable by machines as well as people, because a large share of discovery now happens through search results and AI answers rather than through typed queries.

  • Semantic structure. Real headings, real landmarks, real lists, so the meaning of a page is recoverable without reading the stylesheet.
  • Structured data. Organization, WebSite, SoftwareApplication, FAQPage and BreadcrumbList markup where it genuinely describes the page, validated so it is not decorative.
  • Plain factual claims. Definitional statements written so they can be quoted accurately and lifted without losing their meaning — this documentation is written that way deliberately.
  • Canonical URLs and correct metadata. Every page declares one canonical address, a title and a description that describe it rather than describing the site.
  • Fast, stable, crawlable output. Server-rendered HTML means crawlers see the content in the first response.

Security approach

Security work follows the same principle as everything else: keep it simple enough that one person can reason about all of it.

  • Least privilege. Administrative and data access is restricted to what each component genuinely needs.
  • Everything behind HTTPS, with redirection away from insecure requests.
  • No credentials in the browser. Integration secrets stay on the server, which is why integrations are called server-side.
  • Input treated as untrusted. Anything a visitor can influence is validated before it is used, and output is escaped according to where it is going.
  • Requests authenticated and authorised before they take effect, not merely when the interface is opened.
  • Dependency review. Third-party code is added sparingly and reviewed before it lands, because supply chain risk is the part nobody budgets for.
  • Documented private reporting route. Vulnerabilities are reported privately, not filed as public issues.

Vulnerabilities can be reported through SECURITY.md. Genuine reports are acknowledged and fixed.

Privacy properties

On Anime Array, the privacy properties are structural rather than promised, which means they hold because of how the platform is built rather than because of a policy document.

Because accounts are optional and every core feature works without one, the platform does not need to collect an email address from someone who just wants a recommendation. Because integrations run server-side, advertising and service identifiers are not embedded in page source. Because analytics are used to understand aggregate usage rather than to build a profile of individuals, and site administrators are excluded from reporting so internal traffic does not distort the figures, the data collected is small on purpose.

How new work ships

Every change follows the same shape: small, reversible, readable, and verified before it lands. A change that cannot be undone in a single step needs a stronger justification than usual.

  1. Define the problem in a sentence, including who has it.
  2. Make it work without scripting where that is possible, then add the enhancement.
  3. Check it on a throttled mobile connection before anything else is considered done.
  4. Check it with a keyboard and confirm the focus order makes sense.
  5. Check contrast, labels and live regions as part of the same pass.
  6. Verify on a real device, not only in a desktop emulator.
  7. Keep the revert path intact, and confirm it works before shipping.

Known constraints

Stating limitations is more useful than claiming completeness. Anime Array currently depends on English, covers twelve characters in roleplay with more requested and in progress, has no group or multi-character conversations yet, has no watchlist import from external tracking services, and carries no mobile or desktop application — the platform is the website. Where a feature does not exist yet, it does not exist yet, and the roadmap is written in intentions rather than promises.

Learning more
